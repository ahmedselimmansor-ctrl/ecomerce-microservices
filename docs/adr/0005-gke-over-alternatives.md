# ADR 0005 — GKE بدل Cloud Run أو Autopilot أو Compute Engine MIGs

**الحالة:** مقبول · **التاريخ:** 2026-08-14

## السياق

عشر خدمات بثلاث لغات تحتاج منصة تشغيل على Google Cloud. ثلاث حقائق في هذا النظام تحكم الاختيار أكثر من أي معيار عام:

1. **أربع خدمات مستهلكة لـ Kafka تعمل باستمرار** — لا تنتظر طلب HTTP لتستيقظ.
2. **OpenSearch يعمل داخل العنقود** — لا يوجد مقابل مُدار له على Google Cloud، فنستضيفه بأنفسنا. وهذا يعني عبئًا ذا حالة (StatefulSet + أقراص مستمرة + `vm.max_map_count` + قفل الذاكرة).
3. **خدمات Java تحتفظ بـ connection pools** طويلة العمر نحو Cloud SQL.

أي منصة لا تستوعب الثلاثة معًا مستبعدة، مهما كانت أرخص.

## القرار

**GKE Standard** — عنقود إقليمي (regional) في `me-central1` بعُقد خاصة (private nodes)، مع node auto-provisioning و cluster autoscaler، و Workload Identity للهوية، و Spot VMs للأحمال بلا حالة.

## البدائل التي دُرست فعلًا

### 1. Cloud Run

المرشّح الأقوى، ويستحق جدية أكثر مما يُعطى عادة: يشغّل حاوية بأي لغة، بلا عنقود ولا ترقيات ولا عُقد، ويتوسّع من صفر، والفوترة بالطلب.

سقط على ثلاث نقاط محدّدة، لا على «التعقيد» بشكل مجرّد:

- **المستهلكون الدائمون يُبطلون نموذج التسعير.** مستهلك Kafka لا يُستدعى بطلب؛ ليبقى حيًّا نحتاج `--min-instances` و `--no-cpu-throttling`، أي أن ندفع ثمن CPU مخصّص على مدار الساعة. عندها نكون قد دفعنا تكلفة خادم دائم وخسرنا السبب الوحيد لاختيار Cloud Run.
- **OpenSearch لا يُستضاف عليه أصلًا.** لا أقراص مستمرة، ولا هوية شبكية ثابتة، ولا ضبط sysctl. كنا سنحتاج عنقودًا إلى جانب Cloud Run على أي حال — ومنصتان أسوأ من واحدة.
- **التوسّع بعمق الطابور غير متاح.** التوسّع في Cloud Run مدفوع بالطلبات والتزامن، لا بـ consumer lag. ما نريده هو ما يفعله KEDA بالضبط: اقرأ تأخر مجموعة المستهلكين وارفع النسخ.

في المقابل، ما كسبناه بالتخلي عنه صريح: تشغيل العنقود صار مسؤوليتنا.

### 2. GKE Autopilot

نفس Kubernetes، لكن Google تدير العُقد وتفوتر بالـ pod. مغرٍ جدًا: يحذف تقريبًا كل عمل إدارة العُقد ويأتي بإعدادات أمان مشدّدة افتراضيًا.

**استُبعد بسبب OpenSearch تحديدًا.** Autopilot يقيّد ما نحتاجه حرفيًا لتشغيله: لا `privileged`، ولا DaemonSet لضبط `vm.max_map_count` على العقدة، ولا تحكم في شكل الآلة أو نوع القرص، ولا `memlock` بلا حدود. عبء بلا حالة خالص كان سيعمل عليه بلا شكوى — لكن عبئنا ليس كذلك.

نقطة ثانية أقل حسمًا: تسعير الـ pod أغلى من تسعير العقدة عند استغلال ثابت ومرتفع، وهذه حالتنا (خدمات تعمل 24/7 ونحن من يحشوها في العُقد).

### 3. Compute Engine MIGs + حاويات

أرخص خيار وأبسط نموذج ذهني: مجموعات نسخ مُدارة تشغّل حاويات، خلف موازن حمل.

مرفوض لأن الطريق منه إلى متطلباتنا هو إعادة بناء Kubernetes بجودة أسوأ: جدولة، اكتشاف خدمات، تحديثات تدريجية، حقن أسرار، حشو الموارد، فحوص صحة على مستوى الحاوية لا الآلة. هذا العمل مُنجَز ومُختبَر في مكان آخر.

### 4. GKE Standard ← المختار

## متى يكون هذا القرار خاطئًا

بصراحة، وأصرح مما كان يُقال على منصات أخرى: **لو لم يكن البحث بـ OpenSearch متطلبًا، ولفريق من ثلاثة مهندسين، فـ Cloud Run هو الجواب الصحيح على Google Cloud.**

المزيج «Cloud Run + Pub/Sub push + Cloud SQL + Firestore» يمحو تقريبًا كل العمل التشغيلي في هذا المستند: لا ترقيات عنقود، ولا إضافات، ولا تشخيص CNI، ولا NetworkPolicy. وهو خيار أقوى بكثير من مكافئاته على السحابات الأخرى، لأن Cloud Run يقبل أي حاوية بأي لغة بلا تكيّف.

القرار مبرَّر هنا لأن: (1) OpenSearch بلا مقابل مُدار فنحتاج عنقودًا على أي حال، (2) أربعة مستهلكين دائمين يستفيدون فعلًا من التوسّع بعمق الطابور، (3) الهدف المعلن معمارية microservices كاملة بتحكم صريح في الجدولة والشبكة.

## تفاصيل التنفيذ

| القرار | التفصيل |
|---|---|
| عنقود إقليمي | الـ control plane منسوخ عبر `me-central1-a/b/c` — ترقياته وسقوط نطاق كامل لا يقطعان الـ API |
| عُقد خاصة | بلا عناوين عامة؛ الخروج عبر Cloud Router + Cloud NAT فقط |
| node auto-provisioning | ينشئ مجموعات عُقد بأشكال مناسبة عند الحاجة بدل مجموعات ثابتة نخمّن حجمها مسبقًا |
| `optimize-utilization` | ملف تعريف التوسّع: دمج أسرع للعُقد الفارغة — مقبول لأن كل خدمة عليها PDB |
| Spot VMs | للخدمات بلا حالة · **عُقد عادية إلزامية** لـ order/payment/inventory |
| مجموعة عُقد للنظام | عادية وبـ taint — لا نريد سحب Spot من تحت CoreDNS أو مستقبِل المقاييس |
| Workload Identity | كل ServiceAccount مربوط بحساب خدمة GCP — لا مفتاح JSON في أي حاوية |
| معمارية المعالج | `amd64` افتراضيًا. عائلات Arm (Axion / C4A) ليست في كل منطقة — تحقّق من توفرها في `me-central1` قبل الالتزام بها في الصور |
| قناة الإصدار | `regular` مع نافذة صيانة — الترقيات تلقائية، وهذا يعني أن تتبّع الإهمالات (deprecations) واجب لا اختياري |

```yaml
# الخدمات الحرجة: سحب Spot أثناء معالجة طلب = معاملة معلّقة.
# على GKE لا يكفي عدم طلب Spot — يجب منعها صراحةً، لأن
# node auto-provisioning قد ينشئ عُقد Spot ويجدها الجدولُ متاحة.
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: cloud.google.com/gke-spot
              operator: DoesNotExist
```

```yaml
# الخدمات بلا حالة: تطلب Spot صراحةً وتتحمّل الـ taint المرافق
nodeSelector:
  cloud.google.com/gke-spot: "true"
tolerations:
  - key: cloud.google.com/gke-spot
    operator: Equal
    value: "true"
    effect: NoSchedule
```

## العواقب

**إيجابًا:** مرونة كاملة في الجدولة والشبكة · نظام أدوات ناضج (KEDA · Argo CD · Prometheus · Cloud Service Mesh) · قابلية نقل حقيقية · مكان واحد يستضيف الخدمات و OpenSearch معًا · Workload Identity يُلغي المفاتيح الثابتة تمامًا.

**سلبًا:** تعقيد تشغيلي حقيقي · الترقيات التلقائية في قناة `regular` تفرض متابعة الإهمالات وضبط PDB بعناية وإلا قطعت الترقية الخدمة · حاجة لخبرة Kubernetes في الفريق · ~73$/شهر ثابتة لإدارة العنقود قبل أي عقدة · عبء تشغيل OpenSearch بأنفسنا (لقطات، إعادة توازن، ترقيات) وهو الجزء الذي سيؤلم أولًا.
