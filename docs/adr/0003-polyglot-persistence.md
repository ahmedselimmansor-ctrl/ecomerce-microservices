# ADR 0003 — تعدد مخازن البيانات

**الحالة:** مقبول · **التاريخ:** 2026-08-14

## السياق

استخدام قاعدة بيانات واحدة لكل شيء يعني إجبار أحمال مختلفة جذريًا على نموذج واحد. استخدام قاعدة مختلفة لكل خدمة بلا مبرر يعني تكلفة تشغيلية بلا مقابل. نحتاج قاعدة قرار واضحة.

## القرار

**القاعدة:** اختر المخزن حسب شكل البيانات ومتطلبات الاتساق، لا حسب الحداثة.

| المخزن | الخدمات | المبرر |
|---|---|---|
| PostgreSQL (Cloud SQL) | identity · order · payment · inventory | معاملات ACID · علاقات · متطلبات محاسبية · قيود على مستوى القاعدة |
| MongoDB (Atlas على GCP) | catalog | مخطط المنتج يختلف جذريًا بين الأقسام · قراءات مستندية · لا JOINs |
| Redis (Memorystore) | cart · caching · rate limiting | زمن استجابة تحت المللي · انتهاء صلاحية طبيعي · بيانات قابلة للفقد |
| OpenSearch (مُدار ذاتيًا على GKE) | search | بحث نصي عربي/إنجليزي · facets · لا يمكن لـ SQL أو Mongo فعله بكفاءة |
| Firestore (Native mode) | idempotency · sessions | مفتاح واحد · TTL على مستوى الحقل · لا إدارة سعة |

## التفصيل: لماذا MongoDB للكتالوج؟

هذا القرار الأكثر إثارة للجدل. المبرر ملموس:

```javascript
// موبايل
attributes: { storage: "128GB", ram: "6GB", screen: "6.1\"", sim: "eSIM" }

// حذاء
attributes: { size: "42", width: "D", material: "Mesh", closure: "Laces" }

// عطر
attributes: { volume: "100ml", concentration: "EDP", family: "Woody" }
```

في PostgreSQL خياران: جدول EAV (استعلامات بشعة وأداء سيئ) أو `JSONB` (يعمل، لكن عندها نستخدم PostgreSQL كقاعدة مستندية على أي حال). المستند هو الشكل الطبيعي، والقراءة الغالبة هي «أعطني المنتج كاملًا» — نفس الشكل المخزَّن.

**ولماذا ليس MongoDB للطلبات؟** الطلبات تحتاج ACID حقيقيًا وتقارير مالية وقيودًا على مستوى القاعدة (`CHECK (reserved <= on_hand)`). PostgreSQL أفضل بوضوح.

## البدائل المرفوضة

| البديل | سبب الرفض |
|---|---|
| PostgreSQL لكل شيء (JSONB + pg_trgm) | يعمل حتى حجم معيّن. البحث بـ `pg_trgm` لا يقارَب بجودة OpenSearch للعربية، والسلة في PostgreSQL هدر واضح |
| MongoDB لكل شيء | المعاملات متعددة المستندات موجودة لكنها ليست نقطة قوة، والتقارير المالية أضعف |
| مخزن واحد لكل خدمة بلا استثناء | تكلفة تشغيلية بلا مقابل حقيقي |

## العواقب

**إيجابًا:** كل حِمل على المخزن الأنسب · التوسع مستقل لكل مخزن · لا خدمة تعطّل أخرى بحملها.

**سلبًا:** خمسة أنواع مخازن تحتاج خبرة ومراقبة ونسخًا احتياطية · لا JOIN عبر الخدمات (يعالجه الـ BFF بجلب دفعي) · تكلفة أعلى · اتساق نهائي بين الكتالوج وفهرس البحث (ثوانٍ) · **OpenSearch هو المخزن الوحيد بلا مقابل مُدار على Google Cloud**، فترقيته وإعادة توازن الـ shards ولقطاته عبء علينا لا على المزوّد — وهذه ضريبة حقيقية دفعناها مقابل جودة البحث العربي.

**قاعدة الحماية:** الفهارس المشتقة (OpenSearch، كاش التوصيات) **ليست مصدر حقيقة** ويمكن إعادة بناؤها بالكامل من Kafka. هذا ما يجعل الاتساق النهائي مقبولًا هنا.
