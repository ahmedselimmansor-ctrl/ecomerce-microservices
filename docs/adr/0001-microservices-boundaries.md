# ADR 0001 — حدود الخدمات

**الحالة:** مقبول · **التاريخ:** 2026-08-14

## السياق

تقسيم خاطئ للخدمات أسوأ من عدم التقسيم: خدمات تتشارك قاعدة بيانات، أو تتغير معًا دائمًا، تجمع سوء الاثنين — تعقيد التوزيع بلا استقلاليته.

## القرار

قسّمنا حسب **حدود السياق (bounded contexts)** لا حسب الطبقات التقنية:

| الخدمة | يملك | لا يملك |
|---|---|---|
| identity | المستخدم، العناوين، الجلسات | الطلبات، الدفع |
| catalog | المنتج، القسم، السعر المعروض | المخزون، السعر المدفوع |
| inventory | كمية المخزون والحجز | تسعير المنتج |
| order | دورة حياة الطلب، الـ Saga | بيانات المنتج، رصيد المخزون |
| payment | المعاملة المالية | حالة الطلب |
| cart | نية الشراء قبل الطلب | التسعير النهائي |
| search / recommendation | فهرس مشتق قابل لإعادة البناء | مصدر الحقيقة |
| notification | التسليم عبر القنوات | لماذا نُرسل |

**اختبار الحدود المستخدم:** إن كان تغيير متطلب واحد يجبرنا على تعديل خدمتين ونشرهما معًا، فالحد خاطئ.

## البدائل المرفوضة

| البديل | سبب الرفض |
|---|---|
| Modular monolith | صحيح لفريق صغير، لكن الهدف المعلن هو معمارية microservices على Google Cloud |
| خدمة لكل كيان (20+) | ضريبة شبكة ومراقبة أكبر من قيمة الفصل |
| فصل CRUD (read/write services) | تقسيم تقني لا مجالي — يبعثر منطق العمل |

## العواقب

**إيجابًا:** كل خدمة تُنشر وتتوسع مستقلة · تعدد اللغات ممكن · عزل الأعطال · فرق مستقلة.

**سلبًا:** لا معاملات موزّعة (نحتاج Saga) · الاستعلامات المركّبة تصبح aggregation في الـ BFF · تشخيص أصعب (يعالجه التتبّع الموزّع) · تعقيد تشغيلي حقيقي.

**نقاط ضعف مقبولة الآن:** `inventory` صغيرة جدًا وقد تُدمج في `catalog` لو لم تكن متطلبات الاتساق مختلفة جذريًا (ACID مقابل eventual).
