# ADR 0002 — Saga بدل المعاملات الموزّعة

**الحالة:** مقبول · **التاريخ:** 2026-08-14

## السياق

إنشاء طلب يمس ثلاث قواعد بيانات: الطلب (PostgreSQL/order) والمخزون (PostgreSQL/inventory) والدفع (PostgreSQL/payment). نحتاج ضمانًا بأن الثلاثة تتفق: لا طلب مؤكَّد بلا مخزون محجوز، ولا خصم بلا طلب.

## القرار

**Saga مُنسَّقة (orchestration)** مع تعويض، و`order-service` هو المنسّق.

```
order.created → inventory.reserved → payment.requested
              → payment.authorized → order.confirmed
```

التعويض عند الفشل: `order.cancelled` ⇒ `inventory.release` و `payment.void`.

## البدائل المرفوضة

### 1. Two-Phase Commit (2PC)

مرفوض. XA يقفل الموارد طوال المعاملة، وسقوط المنسّق يترك أقفالًا معلّقة. على مقياس متجر إلكتروني في ذروة الطلب، هذا يعني توقفًا كاملًا. كما أن MongoDB و Kafka لا يشتركان في نفس معاملة XA أصلًا.

### 2. Saga بالتناغم (choreography)

كل خدمة تستمع وتردّ بلا منسّق. أبسط في البداية، لكن الإجابة على سؤال «لماذا عَلِق هذا الطلب؟» تتطلب قراءة كود خمس خدمات وتتبّع سلسلة أحداث ضمنية. اخترنا الـ orchestration لأن **حالة الطلب مركزية وواضحة في مكان واحد**:

```java
// OrderStatus.java — الانتقالات المسموحة صريحة
case PENDING          -> next == AWAITING_PAYMENT || next == CANCELLED;
case AWAITING_PAYMENT -> next == CONFIRMED || next == CANCELLED;
```

### 3. نداءات متزامنة متسلسلة

`POST /orders` ينادي المخزون ثم الدفع ويردّ. أبسط للفهم، لكن زمن الاستجابة = مجموع كل النداءات، وسقوط أي خدمة يعني فشل الشراء. أسوأ من ذلك: الفشل في المنتصف يترك مخزونًا محجوزًا بلا طلب.

## آليات الضمان

| الخطر | الآلية |
|---|---|
| فقدان حدث بعد الكتابة | **Transactional Outbox**: الطلب وحدثه في معاملة واحدة |
| تسليم مزدوج من Kafka | جدول `processed_events(event_id, consumer)` في كل مستهلك |
| حجز عالق بعد فشل الـ Saga | `expires_at` + مهمة تحرير دورية كل دقيقتين |
| حدث متأخر يفسد الحالة | آلة حالة تمنع الانتقالات غير المسموحة |
| رسالة سامّة تحجب الـ partition | DLQ بعد استنفاد المحاولات |

## العواقب

**إيجابًا:** لا أقفال موزّعة · كل خدمة تسقط مستقلة · المسار يتحمّل ذروة عالية (Kafka يستوعب الحِمل) · مسار التعويض مُختبَر فعليًا (البوابة الوهمية ترفض 10% عمدًا).

**سلبًا:** الاتساق نهائي لا فوري — المستخدم يرى `PENDING` لثوانٍ · منطق التعويض كود إضافي يجب اختباره · التشخيص يحتاج تتبّعًا موزّعًا.

**قياس واقعي:** في الاختبار المحلي تستقر الـ Saga خلال 2–5 ثوانٍ من `PENDING` إلى `CONFIRMED`.
