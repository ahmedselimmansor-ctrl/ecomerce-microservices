# 02 — خدمات Google Cloud المستخدمة

جدول شامل لكل خدمة Google Cloud في هذا التصميم: ما تفعله عندنا بالضبط، لماذا اخترناها، وما البديل الواقعي الذي رفضناه — ثم المقابل المحلي أثناء التطوير.

> **ثوابت تسري على كل ما يلي.** الإقليم `me-central1` (الدوحة) على ثلاثة نطاقات `a`/`b`/`c` — أقرب إقليم زمنًا لعملائنا في مصر والخليج. بادئة التسمية `topchoice-dev` / `topchoice-prod` في كل مورد. وGoogle Cloud يستخدم **labels** لا tags: أحرف صغيرة وأرقام و`-` و`_` فقط، فأي وسم فيه حرف كبير أو مسافة يرفضه الـ API لا الـ linter.

## 1. الحوسبة والحاويات

| الخدمة | ما تفعله عندنا | لماذا هي، والبديل |
|---|---|---|
| **GKE Standard (regional, private nodes)** | تشغيل كل الـ microservices | العنقود إقليمي: الـ control plane منسوخ على ثلاثة نطاقات، فترقية أو سقوط نطاق لا يفقدنا الـ API server. والعُقد بلا عناوين خارجية، خروجها عبر Cloud NAT فقط. **البديل:** GKE Autopilot — يزيل إدارة العُقد كليًا لكنه يمنعنا من `DaemonSet` منخفض المستوى ومن ضبط الـ sysctl الذي يحتاجه OpenSearch، ويجعل تشغيل عنقود بحث داخل العنقود صعبًا. Cloud Run كان سيغطي الخدمات عديمة الحالة وحدها ويترك المستهلكين طويلي العمر بلا بيت |
| **Node auto-provisioning (NAP) + Cluster Autoscaler** | إنشاء node pools تلقائيًا حسب طلبات الـ pods، وحذفها عند الفراغ | نفس الدور الذي كان يؤديه محرّك التوفير التلقائي السابق، لكن مدمجًا في الخدمة المُدارة بدل مكوّن نثبّته ونحدّثه ونراقب صحته. **البديل:** node pools ثابتة مع autoscaler لكل واحدة — أبسط في الفهم، أغلى في الفاتورة لأننا ندفع ثمن أكبر شكل حاجة متوقّعة طوال الشهر |
| **Spot VMs** | العُقد التي تستضيف الخدمات عديمة الحالة | خصم يصل إلى ~70%. الإخطار قبل السحب 30 ثانية فقط (أقصر مما اعتدناه)، لذلك `terminationGracePeriodSeconds` و PDB ليسا تزيينًا هنا. `order` و`payment` على عُقد عادية عبر `nodeSelector` |
| **أنواع الآلات — `n2d` / `c3d`، و`c4a` عند توفره** | عُقد العنقود | `n2d`/`c3d` (AMD EPYC) هما الخيار الآمن في `me-central1`. معالج Arm من Google هو **Axion (`c4a`)** ومكسب السعر/الأداء عليه حقيقي لأحمال Java و Node، لكن توفّر عائلات Arm يتفاوت بين الأقاليم بشكل ملموس — لذلك نبني الصور **multi-arch**، حتى لا يتحوّل قرار عائلة الآلة إلى قرار وقت بناء لا يمكن التراجع عنه بلا إعادة نشر |
| **Cloud Run** | مهام دفعية ومهام cron ومعالج تحويل الصور | لا عُقد ندير حجمها، وينزل إلى الصفر بين التشغيلات. **البديل:** `Job` داخل GKE — يوفّر بضعة دولارات ويشغل عُقدًا لأجل مهمة تعمل دقيقتين يوميًا |
| **Cloud Run functions** | معالجة الصور عند الرفع، تقارير، مهام مجدولة | مشغَّلة من Eventarc (أحداث Cloud Storage) ومن Cloud Scheduler |
| **Artifact Registry** | مستودع صور Docker وحزم npm/Maven | مستودع واحد لكل أنواع الحزم بدل مستودع لكل نوع. مفعّل عليه فحص الثغرات (Artifact Analysis) و`immutable_tags` و cleanup policies. **البديل:** Docker Hub خاص — يضيف خروجًا عبر الإنترنت لكل سحب صورة، ويُبطل ميزة أن السحب من داخل نفس الإقليم مجاني |

## 2. الشبكة والحافة (Edge)

| الخدمة | ما تفعله عندنا | لماذا هي، والبديل |
|---|---|---|
| **VPC network + subnetworks** | شبكة واحدة، subnet لكل غرض: عُقد GKE، نطاقات ثانوية للـ pods والـ services، ونطاق محجوز للوصول الخاص | شبكات Google **عالمية** والـ subnets إقليمية — لا حاجة لـ peering بين أقاليم لاحقًا. ولا يوجد تقسيم public/private كما اعتدنا: «الخصوصية» هنا نتيجة غياب عنوان خارجي على الآلة، لا نتيجة جدول توجيه منفصل |
| **Cloud Router + Cloud NAT** | خروج للإنترنت من العُقد الخاصة | بوابة NAT واحدة إقليمية تخدم النطاقات الثلاثة، بدل بوابة لكل نطاق. أرخص وأبسط، ومع ذلك ليست نقطة فشل واحدة لأنها خدمة مُدارة موزّعة لا آلة. الفخ الحقيقي: **نفاد المنافذ** — نضبط `min_ports_per_vm` صراحة ونراقب `nat_allocation_failed` |
| **Global external Application Load Balancer** | استقبال كل حركة HTTPS | عنوان anycast **واحد** يخدم العالم من أقرب نقطة حضور. وهذا يلغي حاجتنا لتوجيه DNS حسب زمن الاستجابة أصلًا. الخلفيات NEGs تشير إلى الـ pods مباشرة (container-native LB)، فلا قفزة `kube-proxy` إضافية ولا هدر عبر النطاقات |
| **Cloud CDN** | الأصول الثابتة وصور المنتجات وصفحات Next.js المخزّنة | ليس منتجًا منفصلًا بل خانة تُفعَّل على الـ backend service للموازِن نفسه. **الثمن:** إبطال الكاش محكوم بحصة صارمة، فلا يصلح آليةً أساسية — نعتمد على مسارات موسومة بالإصدار و TTL قصير مع `stale-while-revalidate`. للفيديو الثقيل البديل هو Media CDN، ولا نحتاجه |
| **Cloud Armor** | حماية OWASP Top 10، وقواعد على معدّل الطلبات لـ `/login` و`/checkout`، وحماية DDoS | قواعد جاهزة مبنية على ModSecurity CRS (`sqli-stable`، `xss-stable`، `lfi-stable`…)، و`rate_limit_options` بحظر مؤقت بدل رفض دائم. Adaptive Protection يكشف أنماط L7 غير المعتادة. **البديل:** WAF من مورّد ثالث أمام الموازِن — طبقة إضافية وزمن إضافي مقابل قواعد لا نحتاجها اليوم |
| **reCAPTCHA Enterprise** | تمييز الـ bots على التسجيل والدفع | مقابل ميزة إدارة الـ bots المدمجة في جدران الحماية الأخرى. يتكامل مع Cloud Armor عبر `bot management` |
| **Cloud DNS** | نطاقاتنا، وسجلات SPF/DKIM/DMARC لمزوّد البريد | anycast عالمي و SLA 100%. **فرق يستحق الذكر:** لا يوجد توجيه حسب زمن الاستجابة كما كنا نستخدمه — المتاح geolocation و weighted و failover. لكننا لا نفتقده: العنوان الـ anycast للموازِن يقوم بالمهمة على مستوى الشبكة لا على مستوى DNS، وهو أدق لأنه لا يعتمد على موقع مُحلِّل الـ DNS |
| **Certificate Manager** | شهادات TLS مُدارة ومتجددة تلقائيًا | مجانية، والتجديد ليس مهمة أحد. تدعم عشرات آلاف النطاقات (مفيد لو صرنا نستضيف نطاقات التجار). **البديل:** `google_compute_managed_ssl_certificate` الأبسط — يكفي لنطاق واحد لكنه لا يعرف wildcard عبر DNS authorization |
| **Private Service Connect** | الوصول إلى MongoDB Atlas بعنوان داخلي من شبكتنا | لا حركة تخرج إلى الإنترنت العام، ولا حاجة لفتح قوائم عناوين عند المورّد. **البديل:** VPC peering مع Atlas — يعمل، لكنه يدمج نطاقات العناوين ويخلق تعارضات عند التوسع |
| **Private Service Access (VPC peering)** | الوصول إلى Cloud SQL و Memorystore | هو الآلية التي تفرضها هاتان الخدمتان: نحجز نطاق `/16` مرة واحدة (`google_compute_global_address` + `google_service_networking_connection`) وننساه. الخطأ الشائع: حجز نطاق ضيق ثم اكتشاف أنه لا يتسع لعنقود Redis بعد سنة |
| **Private Google Access** | وصول العُقد الخاصة إلى Cloud Storage و Firestore و Pub/Sub و Secret Manager | يوفّر علينا تمرير حركة الـ API عبر Cloud NAT — وهذا **بند تكلفة حقيقي** لا تحسينًا نظريًا، لأن Cloud NAT يُفوتر على البايت المعالَج |

## 3. قواعد البيانات والمخازن

| الخدمة | ما تفعله عندنا | لماذا هي، والبديل |
|---|---|---|
| **Cloud SQL for PostgreSQL — Enterprise Plus, regional HA** | `identity` · `order` · `payment` · `inventory` | نسخة احتياطية متزامنة في نطاق آخر مع تحويل تلقائي، صيانة شبه بلا انقطاع (تقاس بالثواني لا الدقائق)، و**data cache** على SSD محلي يقلب أداء القراءات العشوائية. نسخ احتياطي 35 يومًا و PITR. **البديل الجاد:** AlloyDB for PostgreSQL — أقرب مطابقة قدرةً لما تركناه، وأسرع في الاستعلامات التحليلية بفارق حقيقي، لكنه أغلى ويضيف طبقة توافق لا نحتاجها لأن استعلاماتنا معاملاتية قصيرة. Spanner كان سيعطينا توسعًا أفقيًا للكتابة بثمن إعادة كتابة طبقة البيانات وفاتورة من فئة أخرى |
| **Cloud SQL Auth Proxy (sidecar)** | قناة مصادَقة ومشفَّرة من كل pod إلى قاعدة البيانات | مصادقة بهوية الـ ServiceAccount (Workload Identity) بلا كلمة مرور على المسار، وبلا الحاجة لعنوان IP خاص مكشوف. **اعتراف مهم:** الـ proxy **ليس مجمِّع اتصالات**. من كان يعتمد على مجمِّع مُدار في الطبقة الوسطى عليه أن يعرف أن تجميع الاتصالات صار كله مسؤولية HikariCP داخل الخدمة — راجع [04-scalability.md](04-scalability.md) لأثر ذلك على `maximumPoolSize`. إن احتجنا تجميعًا على جانب الخادم فالحل هو PgBouncer كحاوية جانبية ثانية، لا خيار في الخدمة المُدارة |
| **MongoDB Atlas على GCP (عبر PSC)** | كتالوج المنتجات | **لا يوجد MongoDB مُدار من Google.** Firestore ليس متوافقًا مع بروتوكول MongoDB، ولا يدّعي ذلك. البدائل كانت: إعادة كتابة الكتالوج على Firestore أو على PostgreSQL JSONB (ثمن هندسي كبير مقابل مكسب تشغيلي وحيد)، أو تشغيل MongoDB بأنفسنا على GKE (نضيف عنقودًا ثانيًا نحرسه، وقد اكتفينا بواحد للبحث). Atlas يبقى الخيار الأقل كلفة إجمالية. **ملاحظة Terraform:** لا نضيف مزوّدًا خارجيًا — العنقود يُنشأ من واجهة Atlas أو الـ API الخاص بها، وTerraform لدينا يبني **جانب المستهلك فقط**: عنوان داخلي و forwarding rule يشيران إلى service attachment تعطينا إياه Atlas |
| **Memorystore for Redis Cluster** | السلة، الكاش، rate limiting، قوائم الأكثر مبيعًا | نسخة موزّعة على shards مع نسخة قارئة لكل shard وتحويل تلقائي داخل الإقليم، وإعادة توزيع أونلاين. **تنبيه:** هذا منتج مختلف عن Memorystore for Redis العادية (Basic/Standard) التي لا تعرف الـ sharding — الاسم متقارب والفاتورة والسلوك ليسا كذلك |
| **Firestore in Native mode** | الجلسات، مفاتيح الـ idempotency، سلال الضيوف طويلة الأمد | يتوسع تلقائيًا بلا سعة نوفّرها، والحذف التلقائي عبر **TTL policy على حقل زمني** في المستند — وهو بالضبط ما كنا نستخدمه. **الفرق الجوهري:** لا يوجد وضع «سعة محجوزة» أصلًا، فالفاتورة عمليات لا ساعات؛ وحدّ الأداء ليس رقمًا نشتريه بل **توزيع المفاتيح**: مستند واحد يقبل كتابة واحدة في الثانية تقريبًا، والمفاتيح المتسلسلة تصنع نقطة ساخنة. لذلك مفاتيحنا مبنية على معرّفات عشوائية لا على طوابع زمنية |
| **OpenSearch ذاتي الإدارة على GKE** | فهرس المنتجات، البحث النصي العربي/الإنجليزي، الـ facets | **لا مقابل مُدارًا له على Google Cloud** — انظر القسم 11. الشكل: `StatefulSet` بثلاث عُقد بيانات وثلاث عُقد master مخصصة، على Persistent Disk من نوع `pd-balanced`، مع `topologySpreadConstraints` على النطاقات، و snapshots إلى Cloud Storage عبر مستودع `gcs` |

## 4. المراسلة والتكامل

| الخدمة | ما تفعله عندنا | لماذا هي، والبديل |
|---|---|---|
| **Managed Service for Apache Kafka** | ناقل الأحداث الرئيسي — الـ Saga، مزامنة الفهرس، التحليلات | **Apache Kafka حقيقي** لا واجهة متوافقة: نفس المنتجين والمستهلكين ونفس دلالات الـ consumer groups والـ offsets وlog compaction. المصادقة بـ SASL_SSL/OAUTHBEARER بهويات Google Cloud — لا كلمات مرور SASL نديرها. **فرق في التشكيل:** لا نختار «عدد brokers»؛ نحدّد سعة العنقود (`vcpu_count` و`memory_bytes`) وGoogle توزّعها. مريح، لكنه يعني أن حساب «كم partition لكل broker» لم يعد بيدنا مباشرة |
| **Pub/Sub (topics + subscriptions)** | طوابير المهام والإشعارات، الـ fan-out، عزل الفشل | يجمع في منتج واحد ما كان منتجَين: الـ topic يوزّع، والـ subscription هي الطابور الدائم لكل مستهلك، و`dead_letter_policy` يعطي DLQ بلا موارد إضافية. **لماذا لم يحلّ محل Kafka؟** لأن الاستعادة فيه `seek` ضمن نافذة احتفاظ، لا سجل دائم مضغوط. إعادة بناء فهرس البحث من أول الزمن تحتاج سجلًا، والـ Pub/Sub طابور ممتاز لا سجل |
| **Eventarc** | ربط أحداث المنصة (رفع ملف إلى Cloud Storage، تغيّر في Firestore) بمعالِج | يغني عن كتابة مستمعين يدويين لكل مصدر |
| **Cloud Scheduler** | الجدولة الزمنية (cron) | يطلق Cloud Run أو ينشر رسالة Pub/Sub. مُدار، وسجلاته في Cloud Logging مباشرة |
| **Workflows** | (اختياري) Sagas طويلة الأمد مثل مسار الإرجاع/الاسترداد | تنسيق تصريحي بحالة محفوظة. لم نستخدمه للـ Saga الأساسية عمدًا: منطق الطلب يعيش في `order-service` مع بياناته، لا في YAML خارج الكود |
| **Kafka Connect (Debezium) — ذاتي الإدارة** | (بديل إنتاجي) CDC من Cloud SQL إلى Kafka بدل الـ outbox polling | **Datastream** هي خدمة CDC المُدارة من Google وتقرأ WAL من Cloud SQL بلا بنية نديرها، لكن وجهاتها BigQuery و Cloud Storage — **لا تكتب إلى Kafka**. ممتازة للتحليلات، عديمة الفائدة كناقل للـ Saga. لذلك بقي الـ polling هو الافتراضي |

## 5. التخزين

| الخدمة | ما تفعله عندنا | لماذا هي، والبديل |
|---|---|---|
| **Cloud Storage** | صور المنتجات، أصول الواجهة، النسخ الاحتياطية، بحيرة البيانات، وجهة snapshots الـ OpenSearch | دلو إقليمي في `me-central1` بجوار الحوسبة — القراءة من داخل الإقليم بلا رسوم خروج. الوصول من الموازِن عبر backend bucket، ومن الخدمات عبر Private Google Access |
| **Autoclass** | خفض تكلفة الصور نادرة الوصول | ينقل الكائن بين الفئات تلقائيًا حسب استخدامه الفعلي. **البديل:** قواعد عمر يدوية — أرخص بقرش وأدق بالنظرية، لكنها تعني أننا نخمّن نمط الوصول مسبقًا ونصحّح الخطأ باسترجاعات مكلفة |
| **Filestore** | (عند الحاجة) تخزين مشترك NFS لمهام معينة | لم نحتجه بعد؛ الحالة الوحيدة المرشحة هي مساحة عمل مشتركة لمهام معالجة الوسائط |
| **Backup and DR Service** | سياسة نسخ احتياطي موحّدة | Cloud SQL يحتفظ بنسخه الآلية و PITR بنفسه، وAtlas كذلك — هذه الخدمة تغطي أقراص العُقد وأحمال GKE التي لا تملك نسخًا مدمجة، وأهمها أقراص OpenSearch |

## 6. الذكاء الاصطناعي والتوصيات

| الخدمة | ما تفعله عندنا | لماذا هي، والبديل |
|---|---|---|
| **Vertex AI Search for commerce (Retail API)** | محرك التوصيات — ثلاثة نماذج تقديم: «مقترح لك»، «منتجات مشابهة»، وترتيب نتائج البحث المُشخصن | خدمة مبنية للتجزئة تحديدًا: تفهم مفهوم الكتالوج والمنتج والحدث الشرائي بلا أن نُعرّف مخططًا. **البديل:** بناء المحرك بأنفسنا على Vertex AI Vector Search مع embeddings — تحكم كامل ومرونة كاملة، مقابل فريق يملك دورة تدريب وتقييم نماذج، وهو ما لا نملكه اليوم. **قيد عملي:** الكتالوج يسكن `global` لا `me-central1` — لا وجود لكتالوج إقليمي يمكن الإشارة إليه، وهذا يعني أن بيانات المنتجات تغادر الإقليم |
| **استيراد الكتالوج وأحداث المستخدم** | ضخّ المنتجات من Cloud Storage/BigQuery، وبثّ التفاعلات (عرض / إضافة للسلة / شراء) لحظيًا | كتابة الأحداث **مطفأة افتراضيًا** في غير الإنتاج: تصفّح بيئة تطوير يلوّث الكتالوج الحقيقي ولا يمكن سحبه بعد وصوله |
| **Pub/Sub → Dataflow → BigQuery/Cloud Storage** | نقل تدفق التفاعلات إلى المستودع وبحيرة البيانات | يحلّ محل خط النقل المُدار الذي كنا نستخدمه. **الفرق:** Dataflow ليس «اضبط وانسَ» بالكامل — هو وظيفة streaming لها عُقد عاملة وتكلفة مستمرة. المقابل أنه يعالج ويُثري ويُقسّم في الطريق بدل أن يُفرغ خامًا |
| **Vertex AI (Gemini)** | (اختياري) توليد أوصاف المنتجات وتلخيص المراجعات |  |
| **Cloud Natural Language** | تحليل مشاعر المراجعات | يدعم العربية |
| **Cloud Vision (SafeSearch)** | فحص صور المنتجات — محتوى غير لائق ووسم تلقائي |  |
| **Cloud Translation** | ترجمة أوصاف المنتجات عربي↔إنجليزي |  |

## 7. الأمان والهوية

| الخدمة | ما تفعله عندنا | لماذا هي، والبديل |
|---|---|---|
| **GKE Workload Identity** | كل ServiceAccount في العنقود يتقمّص حساب خدمة Google محدد الصلاحيات — لا مفاتيح ثابتة في أي مكان | الربط بصيغة `serviceAccount:${var.project_id}.svc.id.goog[NAMESPACE/KSA_NAME]`. لا ملف مفتاح JSON يُنزَّل، ولا سرّ يُدوَّر، ولا مفتاح يتسرّب في سجل. **البديل:** مفاتيح حسابات خدمة كأسرار Kubernetes — يعمل، وهو أسوأ ممارسة أمنية في المنصة |
| **Secret Manager** | أسرار قواعد البيانات، مفاتيح مزوّد الدفع، مفتاح SendGrid، سرّ JWT | إصدارات مرقّمة وتدوير مجدول وسجل وصول مفصّل. الأسرار مشفّرة بمفتاح CMEK نملكه |
| **External Secrets Operator** | مزامنة الأسرار إلى Kubernetes Secrets | يصادق بـ Workload Identity لا بمفتاح. **البديل:** Secret Manager CSI driver — يركّب السرّ كملف بدل إنشاء `Secret`، أنظف أمنيًا وأصعب على تطبيقات تتوقع متغيّر بيئة |
| **Cloud KMS** | تشفير at-rest لكل مخزن، بمفتاح CMEK مخصص لكل بيئة | التشفير الافتراضي بمفاتيح Google موجود على أي حال؛ CMEK يعطينا **القدرة على الإبطال** — وهي المتطلب الحقيقي في التدقيق، لا التشفير نفسه |
| **Identity Platform** | (بديل/مكمّل لـ `identity-service`) دخول اجتماعي و MFA و SMS OTP | نفس محرك Firebase Auth بواجهة مؤسسية |
| **Security Command Center** | كشف التهديدات، الامتثال، اكتشاف الأصول المكشوفة | يوحّد ما كان ثلاث خدمات منفصلة عندنا سابقًا: كشف التهديدات، لوحة الامتثال، وفحص الثغرات |
| **Artifact Analysis** | فحص ثغرات صور الحاويات عند الدفع وباستمرار بعده | الفحص المستمر هو الفارق: ثغرة تُكتشف بعد أسبوع من النشر تظهر على صورة قائمة، لا على البناء التالي فقط |
| **Binary Authorization** | منع نشر أي صورة غير موقّعة من خط الـ CI | لا مقابل له في ما تركناه — مكسب صافٍ. يقطع طريق «شخص دفع صورة يدويًا إلى الإنتاج» |
| **Organization Policy + Policy Controller** | الحوكمة: منع العناوين الخارجية، فرض CMEK، حصر الأقاليم | `constraints/compute.vmExternalIpAccess` وحده يمنع فئة كاملة من الأخطاء |
| **Cloud Audit Logs** | سجل استدعاءات الـ API للتدقيق | Admin Activity مفعّل ومجاني افتراضيًا؛ Data Access نفعّله انتقائيًا لأنه يولّد حجمًا هائلًا وفاتورة سجلات تفوق ما يبرّره |
| **VPC Service Controls** | (للإنتاج) محيط حول المشروع يمنع تسريب البيانات إلى مشاريع خارجية | الدفاع الوحيد ضد «حساب مخترَق ينسخ الدلو إلى مشروعه». إعداده مُتعب ويكسر أدوات التطوير إن طُبّق بلا حذر، لذلك نضعه في `prod` وحدها |

|---|---|---|

| **Grafana / Cloud Monitoring dashboards** | لوحات المراقبة | Grafana يقرأ من Managed Prometheus مباشرة لمن يفضّل لوحاته الحالية |
| **Cloud Billing + Budgets** | مراقبة التكلفة وتنبيهاتها، وتصدير التفصيل إلى BigQuery | التصدير إلى BigQuery هو ما يجعل السؤال «أي خدمة قفزت الأسبوع الماضي؟» استعلامًا بدل تحقيق |

## 11. ما لا مقابل له على Google Cloud

ثلاث ثغرات حقيقية. ذكرها هنا بصراحة أفضل من اكتشافها في منتصف الانتقال.

### 11.1 البحث — لا OpenSearch مُدار

**لا تقدّم Google Cloud خدمة بحث مُدارة من عائلة Elasticsearch/OpenSearch.** البدائل التي فحصناها:

| الخيار | لماذا رُفض |
|---|---|
| **Vertex AI Search** | محرك دلالي ممتاز، لكنه صندوق شبه مغلق: لا تحكم في BM25، ولا في المحلل الصرفي العربي، ولا في تعريف الـ facets وترتيبها. بحث المتجر عندنا يحتاج هذا التحكم |
| **Elastic Cloud على GCP** | مُدار فعلًا، لكنه مورّد ثالث بفاتورة منفصلة — نفس ثمن Atlas، بلا سبب Atlas (وهو أن الكود مكتوب على بروتوكول MongoDB) |
| **PostgreSQL full-text search** | يكفي لبحث بسيط، وينهار عند الـ facets الديناميكية وترتيب الصلة على ملايين المنتجات |

**ما نفعله:** OpenSearch كـ `StatefulSet` على GKE — نفس الإصدار والصورة التي نستخدمها محليًا.

**ما يكلّفنا ذلك بصراحة:** ترقيات الإصدار الكبرى مهمة يدوية مخطط لها. دورة حياة الـ snapshots إلى Cloud Storage نكتبها ونراقبها. إعادة توزيع الـ shards عند إضافة عُقدة ليست تلقائية بالكامل. ضبط حجم الـ JVM heap ونسبته إلى ذاكرة العُقدة قرارنا. توسيع الـ PVC عملية لا تُلغى. و«العنقود أصفر» يصبح تنبيهًا في نوبة الحراسة عندنا. عمليًا: **يوم عمل هندسي في الشهر تقريبًا في الوضع المستقر**، وأكثر بكثير في شهر الترقية.

### 11.2 البريد — لا خدمة بريد صادر أصلًا

**لا تملك Google Cloud أي خدمة بريد معاملات، ولا حتى واجهة SMTP مُدارة.** وGoogle Workspace ليس بديلًا: حدوده اليومية مبنية على بريد بشري لا على إشعارات آلية.

**ما نفعله:** SendGrid (متاح عبر Google Cloud Marketplace، فتظهر فاتورته ضمن فاتورة Google إن اشتُري من هناك). الاتصال SMTP relay، فكود `notification-service` لا يتغيّر جوهريًا.

**ما يكلّفنا ذلك:** مورّد إضافي في مسار حرج (تأكيد الطلب إشعار لا يُفوَّت). سرّ إضافي في Secret Manager. سجلات SPF و DKIM و DMARC في Cloud DNS نحن مسؤولون عن صحتها. سمعة عناوين IP لا نتحكم بها ولا نراها. وتحقيق أعطال التسليم يمر عبر لوحة مورّد آخر لا عبر Cloud Logging.

### 11.3 حوسبة الحافة — لا مقابل كامل لدوال الـ CDN

لا يوجد على حافة Google ما يعادل تشغيل دالة كاملة عند نقطة الحضور. المتاح **Service Extensions** (إضافات WASM على الموازِن)، وهي أضيق نموذجًا ومتاحة على أنواع محددة من الموازِنات. أثر ذلك ملموس في موضعين: **غرفة الانتظار الافتراضية** وقت الذروة، و**تحويل الصور** إلى WebP/AVIF. الحلّان عندنا: الغرفة تُنفَّذ داخل الـ gateway بـ Redis مدعومة بقواعد المعدّل في Cloud Armor، والصور تُحوَّل في خدمة Cloud Run خلف الموازِن مع Cloud CDN أمامها — قفزة إضافية عند الـ miss، لا شيء عند الـ hit.

## 12. المقابل المحلي أثناء التطوير

| Google Cloud | محليًا |
|---|---|
| Cloud SQL for PostgreSQL | حاوية `postgres:16` |
| MongoDB Atlas | حاوية `mongo:7` |
| Memorystore for Redis Cluster | حاوية `redis:7` |
| Managed Service for Apache Kafka | حاوية `apache/kafka` (KRaft) |
| OpenSearch على GKE | حاوية `opensearchproject/opensearch` — **نفس المحرك ونفس الإصدار**، وهي الفائدة الوحيدة السارّة في إدارته بأنفسنا |
| Pub/Sub | **Pub/Sub emulator** |
| Firestore | **Firestore emulator** |
| Cloud Storage | **fake-gcs-server** |
| SendGrid | **Mailpit** |
| Vertex AI Search for commerce | بديل داخلي قائم على الشعبية (Redis sorted set) — **لا يوجد محاكي لواجهة Retail**، وترك إعداد الـ serving config فارغًا هو الوضع الطبيعي محليًا |
| Cloud CDN + الموازِن العالمي | Next.js dev server |
| GKE | docker-compose |
| Secret Manager | ملف `.env` — **لا يوجد محاكي رسمي**، والفارق مقبول لأن الأسرار المحلية وهمية أصلًا |

الملاحظة الجديرة بالتسجيل: عدد المحاكيات هنا **أكبر** مما كان لدينا، لأن محاكيًا واحدًا كان يغطي عدة خدمات سابقًا بينما هنا لكل خدمة محاكيها الرسمي. الأثر إيجابي عمليًا — المحاكي الرسمي أدق سلوكًا من محاكٍ عام — والثمن إدخالات إضافية في `docker-compose`.

ثلاث ملاحظات على الرقم:

1. **`me-central1` أغلى من الأقاليم الأمريكية** بنحو 15–20% على الحوسبة والتخزين. هذا ثمن قرب زمن الاستجابة، وهو ثمن نقبله عن وعي.
